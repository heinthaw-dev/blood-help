# Quick Task 260925-31f — Search-radius range rings

The requester waiting on RequestLive has no picture of reach. This adds a quiet
concentric-ring graphic driven by the request's real `search_radius_km`, replacing the
idea of a "searching" spinner with something that states a fact: how far the request
has travelled, and how many compatible donors that covers.

Covers the **RequestLive half of Task 5** in quick task
[260925-260](../260925-260-auto-expanding-blood-request-radius-10-t/260925-260-PLAN.md).
Home.tsx feed fix and the `fcm_type=radius_expanded` deep link stay with that task.

## Why rings and not a radar sweep

A rotating radar sweep was considered and rejected:

- It reads as scanning people. The requester never sees donor positions, and
  [SKILL.md](../../../.claude/skills/frontend-design/SKILL.md) forbids raw pins.
- Infinite motion on a screen that stays open 20-30 minutes reads as "stuck", against
  the design system's *emergency calm* rule.
- A sweep implies live detection. The system pushes once per ring and then waits on a
  human. Perpetual motion with zero responders reads as system failure.

Rings are driven by state, animate once per real widening, and rest in between.

## Locked geometry (inherited from 260925-260)

10 km start · +5 km every 3 min while zero responders · 30 km cap · 5 rings total.

## Tasks

### Task 1 — `SearchRadiusRings` component

- **files:** `src/components/SearchRadiusRings.tsx` (new), `src/index.css`
- **action:** Presentational SVG: five concentric rings, one per reachable radius step.
  Rings at or inside the current radius are drawn in primary at low alpha over a faint
  wash; rings beyond it stay as hairlines in `--border-card` so the remaining reach is
  visible without being promised. A centre dot marks the request. **No donor dots and no
  coordinates of any kind.** The newest ring is keyed on `radiusKm` so React remounts it
  on each widening and the `bh-ring-grow` keyframe plays exactly once — no timers, no
  loop. Keyframe added to `index.css` beside the existing RequestLive animations, with a
  `prefers-reduced-motion` kill switch matching the file's convention.
- **verify:** `npm run lint` clean.
- **done:** component renders correct ring count for 10/15/20/25/30 and is static between changes.

### Task 2 — Live radius in RequestLive

- **files:** `src/screens/RequestLive.tsx`
- **action:** Fetch `search_radius_km` for the active request and subscribe to UPDATE on
  that row (channel `rx:${requestId}`, gated on `currentUserId` like the existing
  responders effect). Feed it to the rings and to the donors-within-radius count, which
  is currently pinned to a hardcoded `radius_km: 10` — a real defect once widening runs,
  since the count would stay frozen at the 10 km figure.
- **verify:** `npm run build` clean.
- **done:** radius shown and counted from the request row, updating live.

### Task 3 — Bilingual reach copy

- **files:** `src/screens/RequestLive.tsx`, `src/components/SearchRadiusRings.tsx`
- **action:** Burmese-first line under the rings: donors reached + current radius at
  10 km; "widened to N km" after each expansion; a plain cap line at 30 km. Burmese
  numerals via `formatNumber`. The existing D-09 transparency sentence stays — rings and
  copy live inside that same card rather than adding a second one.
- **verify:** `npm run build && npm run lint` clean.
- **done:** no vague "searching" wording anywhere; every number on screen is one the
  system actually holds.
