# Quick Task 260925-31f — Search-radius range rings

## What shipped

A concentric-ring graphic on RequestLive, driven by the request's real
`search_radius_km`. Five rings, one per radius step; rings at or inside the current
reach are drawn in primary over a faint wash, the rest stay as hairlines so the
remaining reach is visible without being promised. A centre dot marks the request.
Bilingual copy under it states the reach and the compatible-donor count it covers, and
switches to a widening line after each expansion and a plain cap line at 30 km.

It sits inside the existing D-09 transparency card rather than adding a second card —
reach and count are one fact, and the screen's job is the donor list below.

## Why not a radar sweep

The sweep was the original request and was argued down for three reasons, all recorded
in the component's doc comment so it is not re-litigated later:

- A sweep reads as scanning people. The requester never sees donor positions, and the
  design system forbids raw pins. The graphic would promise a map that must not exist.
- RequestLive stays open for 20-30 minutes. Perpetual motion for that long reads as
  "stuck" and works against the *emergency calm* rule.
- A sweep implies live detection. The system pushes once per ring and then waits on a
  human, so a spinning sweep with zero responders reads as system failure rather than
  as silence.

Motion now happens once per real widening: the newest ring is keyed on `radiusKm`, so
React remounts it and `bh-ring-grow` replays exactly once. No interval, no infinite
animation, nothing running while the reach is unchanged. Reduced-motion is handled by
the existing kill-switch block in `index.css`.

## Defect found and fixed

`donors_within_radius` was being called with a hardcoded `radius_km: 10`. The D-09
count is presented to the requester as truthful, but once the widening job runs it
would have stayed frozen at the 10 km figure while the request actually reached 30 km.
It now uses the request's own reach.

## Platform finding — why reach is polled, not subscribed

`blood_requests` is **not** in the `supabase_realtime` publication (verified against the
live DB: only `request_responses` and `donations` are). A `postgres_changes`
subscription on it would have delivered nothing and failed silently — the same class of
failure recorded for the CSP work.

The screen polls every 30s instead, and stops itself on the first responder and at the
cap, mirroring the widening job's own stop rules. Adding `blood_requests` to the
publication is the cleaner long-term fix but is a production schema change and was left
out of a UI task.

Generated types were stale for three migrations (the radius columns, `donors_in_ring`,
`requests_for_donor`), so reading `search_radius_km` was a typecheck error until they
were synced.

## Verification

`npm run build` (tsc + vite) and `npm run lint` both clean. No automated browser tests
per project convention — manual check is the user's.

## Code-quality pass

`code-quality-refactor` reviewed the three files. It replaced the five-deep nested
ternary building the headline with a `ReachStatus` value and a `Record<Lang, ...>` copy
table, matching how the rest of the app stores bilingual strings — strings moved
verbatim, same output for every radius and language. It confirmed the polling effect's
dependency array causes no re-render loop (React bails when the fetched value equals
state, and tears down the old interval before the new run), found no privacy leak, and
found no raw hex.

It flagged one thing for a human call: both reads fed the screen while discarding their
`error`. Fixed with `console.error` rather than the DEV-gated pattern used elsewhere in
the file — `vite.config.ts` strips `console.log/debug/info` in production, which is
precisely how the FCM and QR scanner failures stayed invisible for weeks.
