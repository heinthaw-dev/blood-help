# Quick Task 260925-260 — Auto-expanding request radius

A blood request starts searching at 10 km. While **nobody has responded**, the radius
widens by 5 km every 3 minutes — 10 → 15 → 20 → 25 → 30 — alerting only the donors in
the newly added ring. It stops the moment someone taps "I'll help", or at 30 km, where
the requester is told plainly that maximum range was reached.

No UI control. The requester never picks a number.

## Locked decisions (from the user)

| Decision | Choice |
|---|---|
| Start / step / interval / cap | 10 km, +5 km, every 3 min, stop at 30 km |
| Widening trigger | Zero responders so far — not "zero donors found" |
| Stop condition | First response, or the 30 km cap |
| Requester told | In-app banner on RequestLive **and** an FCM push per widening |
| At the cap | Stop, say so plainly, include the total alerted count |
| Re-alerting | Ring only — a donor already alerted is never buzzed again |

## Platform findings

- **pg_cron 1.6.4 is installed.** Scheduling is available.
- **pg_net is NOT installed.** Required for a cron job to call an edge function over
  HTTP. It is available on the project and needs enabling.
- **`notify-donors` cannot be reused by cron.** It demands a user JWT and calls
  `auth.getUser()` ([index.ts:29-50](../../../supabase/functions/notify-donors/index.ts#L29-L50)).
  A cron job has no user session, so the widening needs its own function.
- **No notifications table exists.** [Notifications.tsx](../../../src/screens/Notifications.tsx)
  is an empty-state shell, so the widening message goes to RequestLive + FCM, not there.

## Tasks

### Task 1 — Schema: radius state on `blood_requests`

- **files:** `supabase/migrations/<ts>_blood_request_radius_expansion.sql`
- **action:** Add three columns:
  - `search_radius_km int not null default 10` — current reach
  - `radius_last_expanded_at timestamptz` — null until the first widening; the next
    widening is due at `coalesce(radius_last_expanded_at, created_at) + 3 min`
  - `radius_cap_notified boolean not null default false` — so the 30 km message is
    sent once, not every minute
  Plus `check (search_radius_km between 10 and 30)`.
- **verify:** existing rows default to 10; constraint rejects 45.
- **done:** columns live, additive, no existing behaviour changed.

### Task 2 — Ring + per-request-radius RPCs

- **files:** same migration or a second one
- **action:**
  - `donors_in_ring(lat, lng, inner_km, outer_km)` — available donors whose distance is
    `> inner_km*1000` and `<= outer_km*1000`. This is what keeps already-alerted donors
    from being buzzed again on every widening.
  - `requests_for_donor(lat, lng)` — requests visible to a donor when
    `dist <= r.search_radius_km * 1000`, i.e. the **request's** reach decides, not a
    constant on the donor's side. New function rather than changing
    `requests_within_radius`, so nothing existing breaks.
- **verify:** ring at (10,15] excludes a donor at 8 km and includes one at 12 km.
- **done:** both callable, `security definer`, `search_path` pinned like the others.

### Task 3 — `expand-request-radius` edge function

- **files:** `supabase/functions/expand-request-radius/index.ts` (new)
- **action:** Authenticates by comparing the bearer token to `SUPABASE_SERVICE_ROLE_KEY`
  (no user JWT, no new secret to invent). For every active request that has **zero**
  rows in `request_responses`, is due by the 3-minute clock, and is under 30 km:
  1. new radius = old + 5, capped at 30
  2. update the row and stamp `radius_last_expanded_at`
  3. `donors_in_ring(old, new)` → filter by `COMPATIBLE_DONOR_TYPES` → FCM to that ring
  4. bump `alerted_count`
  5. FCM to the requester: "expanding to N km"
  At 30 km with `radius_cap_notified = false`: send the cap message once and set the flag.
- **verify:** invoked manually with a seeded request, radius steps 10 → 15 and only
  ring donors receive a push.
- **done:** function source in repo. **Not deployed in this task** — see Hold below.

### Task 4 — `notify-donors` reads the request's radius

## Known limits (worth stating, not fixing here)

- **Ring gaps if a donor moves mid-request.** Rings are computed from the donor's stored
  coordinates at each run. A donor who updates their location between widenings could
  land in no ring, or in two. Rare; the alternative is an `alerted_donors` table.
- **Coarsening blurs every boundary.** [geolocation.ts:48](../../../src/geolocation.ts#L48)
  rounds coordinates to ~1.1 km, so each ring edge carries about a kilometre of slop.
  Deliberate privacy trade, inherited from the existing 10 km behaviour.
- **A donor who was unavailable during an earlier ring is never revisited.** They were
  outside `is_available = true` when their ring was alerted, and the ring does not
  come round again.
- **Timing is minute-granular.** A 1-minute cron means a 3-minute interval fires at
  3-4 minutes in practice.
- **12 minutes to reach 30 km.** Four widenings at 3 minutes. Worth checking against the
  real urgency of an `urgent` request — it may want a faster clock than `today`.
