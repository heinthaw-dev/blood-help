# Quick Task 260925-6qa: Radius parameters are shadowed by table columns

## Problem

Both functions declare parameters named `lat` and `lng`, and both query a table
that has columns named `lat` and `lng`. In a SQL function the table's columns win
the name resolution, so `st_point(lng, lat)` compiles to the row's own position.
Every distance is measured from a row to itself.

Consequences: `dist_meters` is always `0`, and `st_dwithin(x, x, anything)` is
always true — so the radius argument has no effect at all.

Proven against the live database:

```
donors_within_radius(16.78, 96.14, 1)   -- 1 km
→ 3 rows, all dist_meters = 0, including a donor 18 km away

requests_within_radius(16.942649, 96.14, 1) → 5 rows
```

`donors_in_ring` had the identical bug and was fixed in `20260924190553` by
prefixing its parameters `p_`. These two were never given the same treatment.

## Affected call sites

| File | Effect of the bug |
|---|---|
| `supabase/functions/notify-donors/index.ts:95` | Initial alert pushes to every available compatible donor in the database, not the 10 km ring |
| `src/screens/RequestLive.tsx:441` | The D-09 "N compatible donors can see your request" count ignores distance |
| `src/screens/Home.tsx:353` | A donor's feed lists every active request regardless of distance |

## Tasks

### 1. Migration — rename the parameters

File: `supabase/migrations/<version>_fix_radius_param_shadowing.sql`

`create or replace` cannot rename parameters, so each function is dropped and
recreated with `p_lat`, `p_lng`, `p_radius_km`. Bodies are otherwise unchanged.
Both are `security definer` with default `PUBLIC EXECUTE`, which a recreate
restores — no grant changes needed.

Verify: `donors_within_radius(16.78, 96.14, 1)` returns only donors genuinely
within 1 km, with non-zero `dist_meters`.

### 2. Update the three call sites + generated types

Named RPC arguments must match the new parameter names, so all three callers and
`src/types/database.ts` change together. A missed call site fails loudly with a
"function does not exist" error rather than silently — PostgREST resolves
overloads by argument name.

Verify: `npm run build` and `npm run lint` clean; `notify-donors` redeployed.

## Must haves

- `donors_within_radius` and `requests_within_radius` respect their radius argument
  and report true distances.
- No caller still passes `lat`/`lng`/`radius_km` by those names.
- Build and lint green; `notify-donors` redeployed with the new argument names.
