# Quick Task 260925-5gb: Auto-expanding search radius job

## Problem

Migrations `20260924190500` and `20260924190600` shipped the *state* of the
auto-expanding radius (`blood_requests.search_radius_km`,
`radius_last_expanded_at`, `radius_cap_notified`) and the *query*
(`donors_in_ring`), but nothing that moves the state. Verified against the live
database: `cron.job` holds only `auto-expire-requests`, there is no
`expand_request_radius` function, and every open request — including one 66
minutes old — still reads `search_radius_km = 10` with
`radius_last_expanded_at = NULL`.

`RequestLive` polls the column every 30 s and truthfully reports 10 km forever.

## Decisions (locked)

- **Ring alerts are retried.** A durable queue table records each newly reached
  ring; a failed FCM send stays owed and is retried on the next tick. Rationale:
  a radius that moved while its donors were never alerted is the exact silent
  failure the app exists to prevent.
- **Cap message is in-app only, no push.** `SearchRadiusRings` already renders a
  bilingual `capped` headline at 30 km. No service-worker or `App.tsx` change.
  `radius_cap_notified` stays unused, reserved for a future push.
- **`notify-donors` is not reused.** It hard-requires the requester's JWT and
  403s any other caller, and it hardcodes `radius_km: 10`. Ring delivery gets its
  own service-role function.

## Tasks

### 1. Migration — state machine, queue, cron tick

File: `supabase/migrations/20260925000000_radius_expansion_job.sql`

- `create extension pg_net` (available 0.20.3, not yet installed).
- `public.radius_expansion_events` — the ring queue. RLS on, no policies
  (job-internal; service role bypasses).
- `public.expand_request_radius()` — widens every due request by 5 km to a 30 km
  cap in one statement, queues the newly reached ring, returns what it moved.
  Due = `status='active'` AND `search_radius_km < 30` AND no `responding` row AND
  `coalesce(radius_last_expanded_at, created_at) <= now() - interval '3 minutes'`.
  `FOR UPDATE SKIP LOCKED` so overlapping ticks cannot double-bump.
- `public.run_radius_expansion()` — widens first, then POSTs the delivery worker
  via `net.http_post` only if rings are owed. Network failure must never block
  the widening.
- `cron.schedule('expand-request-radius', '* * * * *', ...)`.

Verify: `select * from public.expand_request_radius();` moves a due row and
inserts a matching queue row.

### 2. Edge function — ring delivery

File: `supabase/functions/expand-radius/index.ts`

- Service-role bearer only, constant-time compared against the auto-injected
  `SUPABASE_SERVICE_ROLE_KEY`. `verify_jwt: false` (cron has no user JWT).
- Claim up to 50 pending events, incrementing `attempts` on claim so a crash
  burns an attempt rather than looping forever.
- Per event: re-check the request is still active with zero responders, call
  `donors_in_ring(inner, outer)`, filter by directional compatibility, push
  data-only FCM to that band only, prune dead tokens.
- Settle every terminal outcome by stamping `notified_at` — sent, nothing to
  send, or superseded — so only genuine failures retry.

Verify: function deploys; a seeded pending event settles.

### 3. Wire and verify against live data

- Apply migration, deploy function, seed Vault (`project_url`,
  `service_role_key`).
- Confirm `search_radius_km` moves off 10 on the existing B- request.

## Must haves

- `cron.job` contains an active per-minute expansion job.
- A request older than 3 minutes with zero responders has
  `search_radius_km > 10` and a non-null `radius_last_expanded_at`.
- Each widening leaves exactly one `radius_expansion_events` row whose
  `[inner_km, outer_km)` matches the move.
- Widening still happens when the Vault secrets are absent or the edge function
  is unreachable.

## Out of scope

- Push for the 30 km cap (in-app headline covers it).
- `notify-donors` initial-alert behaviour.
