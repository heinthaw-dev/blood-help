# Quick Task 260819-i0m — Restore deleted seed data

## Situation

The user deleted rows from `profiles` and `donors` in the hosted Supabase
project, including the three fixed-UUID development seed records.

Live state at the start of this task:

| table | rows |
|---|---|
| `auth.users` | 54 |
| `public.profiles` | 0 |
| `public.donors` | 0 |
| `public.blood_requests` | 0 |
| `public.request_responses` | 0 |
| `public.donations` | 0 |
| `public.device_tokens` | 0 |

Every public table is empty — the deletes cascaded through `profiles`'s six
inbound foreign keys. `auth.users` survived (it is the FK *target*, not a
dependent), so 54 auth accounts remain: the 3 `@dev.local` seeds and 51 real
`@bloodhelp.local` phone logins.

There is no seed file in the repo — the original seed was applied ad hoc via
MCP during Phase 06-03 and re-applied after the Phase 07 schema split. That is
why the deletion was not trivially reversible, and it is worth fixing as part
of this task.

## Source of truth for the restored values

Reconstructed from planning artifacts, not invented:

- `.planning/phases/06-foundation/06-03-PLAN.md:129-131` — names, phones, blood
  types, availability, donation counts, coarsened coordinates, languages
- `.planning/phases/07-data-persistence-geo-matching/07-RESEARCH.md:502-504` —
  the same three donors expressed against the post-split `donors` table

## Tasks

### T1 — Write `supabase/seed.sql`

**Files:** `supabase/seed.sql` (new)

**Action:** Check the seed into the repo so this is repeatable. Must be fully
idempotent and safe against a database holding real users — it may only ever
touch the three `00000000-0000-0000-0000-00000000000{1,2,3}` UUIDs. Guard the
`auth.users` bootstrap with `WHERE NOT EXISTS` (not `ON CONFLICT`) so the tuple
is never built when the rows already exist; use `ON CONFLICT DO NOTHING` for
`profiles` and `donors`.

Leave `donor_code` NULL and let the `donors_set_donor_code` BEFORE INSERT
trigger fill it. The Phase 06 literals `ZH001`/`AM002`/`KK003` predate
`generate_donor_code()` and contain `0` and `1`, which are not in its
`A-Z2-7` alphabet — reusing them would put malformed codes in the QR flow.

**Verify:** File reads as valid SQL against the live schema (`profiles` has no
`blood_type`/`township` — those moved to `donors` in Phase 07).

**Done:** `supabase/seed.sql` exists and is idempotent by construction.

### T2 — Apply to the hosted project

**Action:** Execute the seed against the live database via Supabase MCP.

**Verify:**
- `profiles` = 3, `donors` = 3, three distinct `donor_code` values
- `donors_within_radius(16.82, 96.15, 10.0)` → 2 rows (Ko Kyaw excluded,
  `is_available = false`) — matches `06-03-SUMMARY.md:62`
- `leaderboard_top_donors()` → Aye Myint (7) → Zaw Htike (3) → Ko Kyaw (1) —
  matches `260626-igc-SUMMARY.md:32`
- Re-running the inserts leaves counts unchanged

**Done:** Both RPCs return their documented Phase 6 / Phase 9 results.

## Must-haves

- 3 `profiles` rows and 3 `donors` rows at the original fixed UUIDs
- `donor_code` values in the real 5-character `A-Z2-7` format
- `supabase/seed.sql` checked in and safe to re-run
- No fabricated rows for the 51 real user accounts

## Out of scope

- **The 51 orphaned real accounts.** Their profile data (name, blood type,
  location, donation history) existed only in `profiles`/`donors` and is
  unrecoverable — `auth.users` carries only the id and the phone-derived email.
  They are not lost accounts: `hydrateUserFromDb` returns `false` on a missing
  profile (`src/App.tsx:249`), which routes the user back through onboarding,
  and `handleSaveDonor` writes a fresh profile + donor row. They self-heal on
  next login, minus their history. Fabricating rows for them would invent
  medical data (blood types) for real people — not done.
- Seed `blood_requests` / `donations` / `request_responses`. The user asked for
  profiles and donors; request seeds also collide with the
  `one_open_request_per_user` partial unique index.
