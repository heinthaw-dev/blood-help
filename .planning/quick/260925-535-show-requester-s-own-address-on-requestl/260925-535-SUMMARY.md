# Quick Task 260925-535 — Summary

## What was wrong

The location chip on RequestLive read `ရန်ကုန် ဆေးရုံကြီး` for every request. The value was
never read from anywhere: `township` was declared with that string as its default parameter,
and `App.tsx` rendered `<RequestLive>` without the prop. The string is the same example copy
used as the address placeholder hint in CreateRequest.

The requester's real address was already in state and in the database — `requestDraft.address`,
persisted as `blood_requests.current_address` on post and restored from it on reload.

## Changes

| File | Change |
|------|--------|
| `src/App.tsx` | Pass `township={requestDraft?.address}` to `<RequestLive>` |
| `src/screens/RequestLive.tsx` | Removed the hardcoded default; documented the prop as the requester's typed address |
| `src/screens/RequestLive.tsx` | Added `locationLabel = township?.trim()`; the pin + text row renders only when non-empty |
| `src/screens/RequestLive.tsx` | Long addresses truncate with ellipsis and carry a `title` tooltip instead of wrapping the header row |

## Why the empty case hides the row

Substituting a location the requester never entered is a truthfulness problem on an emergency
screen, the same class of issue as the D-09 rule against claiming donors were "alerted". When
there is no address, the row collapses to the blood-type badge alone.

## Verification

- `npm run build` — `tsc -b` type-check plus production bundle, passed.
- `npm run lint` — no errors in `src/` (one pre-existing warning in `.claude/get-shit-done/bin/lib/state.cjs`).
- Manual check pending by the user: post a request with an address and confirm the header shows it.

## Note for testing

RequestLive is served by the PWA service worker (`firebase-messaging-sw.js`, injectManifest with
`precacheAndRoute`). It calls `skipWaiting()` but not `clientsClaim()`, so an already-open tab or
installed PWA can keep serving the previous bundle. Unregister the worker or fully close the
installed app to see this change.
