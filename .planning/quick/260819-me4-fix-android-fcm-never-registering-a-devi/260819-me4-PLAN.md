# Quick Task 260819-me4 — Android never registers an FCM token

## Situation

After `260819-hsx` fixed the CSP, iOS registers and receives push. Android
still receives nothing, and `device_tokens` holds exactly one row (the iOS
device). Android notification permission is granted at the OS/browser level.

This is not a delivery problem — Android has no token row, so `notify-donors`
has nothing to send to. The question is why `enablePush()` is never called on
Android, or never completes.

## Root causes

Four defects, found by tracing every path that can write `device_tokens`.

### A. `PushNudge` has no Android path that calls `enablePush`

`src/components/PushNudge.tsx` wires `handleEnable` (the only function that
calls `enablePush`) to exactly one state: `case 'ios-enable-push'`.

`case 'android-install'` wires `handleInstall`, which calls **only**
`promptAndroidInstall()` and then sets `succeeded` on an `'accepted'` outcome —
rendering the green **"Alerts are on"** card. That message is false: installing
a PWA requests no notification permission and registers no token.

And `deriveState` in `src/lib/pwa.ts` has no `android-enable-push` state at all:

```ts
if (notifPermission === 'granted') return 'granted'   // ← nudge renders null
if (isIOS) { … 'ios-enable-push' … }
if (canInstallAndroid && !isStandalone) return 'android-install'
return 'hidden'
```

So on Android: permission not yet asked → at best an Install button that never
enables alerts; permission already granted → `'granted'` → `PushNudge` returns
`null` and **no manual trigger exists anywhere in the UI**.

The state name `'granted'` is the conceptual error — it conflates *permission
granted* with *alerts working*. A token can be absent in either case.

### B. The silent recovery path races auth hydration

`src/App.tsx:443-455` is the only always-on recovery, and it merely attaches a
`controllerchange` listener:

```ts
function handleControllerChange() {
  if (user.supabaseId && Notification.permission === "granted")
    void enablePush(user.supabaseId);
}
```

The service worker calls `clients.claim()` in its `activate` handler, so
`controllerchange` fires during boot — before `initAuth` has hydrated
`supabaseId`. The guard sees `null` and no-ops. When `supabaseId` arrives later
the effect re-runs, but it only re-attaches the listener; nothing fires. So the
event that was supposed to heal a missing token is reliably missed.

### C. `enablePush` reports success when the database write failed

`src/lib/push.ts` logs the upsert error and then returns `'granted'` anyway, so
the UI shows the success card and callers believe a token exists when it may
not. The error message itself is also discarded.

### D. The stale-token cleanup deletes other devices — will break iOS the moment Android works

```ts
await supabase.from('device_tokens').delete()
  .eq('profile_id', profileId).eq('platform', 'web').neq('fcm_token', token)
```

Every row is written with `platform: 'web'`, so for a user with both an iPhone
and an Android phone this deletes the *other device's* token on every
registration. The two devices would ping-pong, never both receiving alerts.

This is latent today only because Android never registers. Fixing A–C without
fixing D converts "Android broken" into "whichever device registered last".

The delete exists to clear tokens orphaned by FCM rotation. The correct owner of
that cleanup is the send path, which gets authoritative
`registration-token-not-registered` errors back from FCM — and
`supabase/functions/notify-donors/index.ts:164` currently just logs failures
without pruning.

## Tasks

### T1 — Give Android a real enable path

**Files:** `src/lib/pwa.ts`, `src/components/PushNudge.tsx`

**Action:**
- Add `'android-enable-push'` to `PwaState`. In `deriveState`, for non-iOS with
  a usable Notification API and `notifPermission === 'default'`, return it
  (preferring `'android-install'` only when an install prompt was captured and
  the app is not yet installed).
- Wire that case in `PushNudge` to `handleEnable`, reusing the existing
  `enablePrompt`/`enableCta` copy and the error line added in `260819-hsx`.
- Chain `handleInstall` into `enablePush` after an accepted install, so the
  success card is only shown when a token was actually registered.

**Verify:** `npm run build` + `npm run lint` green.

**Done:** An Android user has a tappable path that ends in a `device_tokens`
row.

### T2 — Register the token as soon as the session is known

**Files:** `src/App.tsx`

**Action:** Replace the listener-only `controllerchange` effect with one that
also fires directly when `user.supabaseId` becomes available and
`Notification.permission === 'granted'`. `enablePush` is safe here: with
permission already granted, `Notification.requestPermission()` resolves without
prompting, which the function's own contract already documents. Keep the
`controllerchange` listener for token rotation after a service-worker update.

**Verify:** Effect runs on login and on SW controller change; never prompts when
permission is `'default'`.

**Done:** Any logged-in user with permission granted converges to a registered
token on next app open, on any screen — the general recovery for both platforms.

### T3 — Do not report success on a failed write

**Files:** `src/lib/push.ts`

**Action:** Return `'error'` when the upsert errors, and include the Supabase
error message in the `console.error`.

**Verify:** Build green; `PushNudge` shows its retryable error line on failure.

**Done:** `'granted'` means a row exists.

### T4 — Make token cleanup multi-device safe

**Files:** `src/lib/push.ts`, `supabase/functions/notify-donors/index.ts`,
`supabase/functions/notify-requester/index.ts`

**Action:**
- Remove the per-profile blanket delete from `enablePush`. The
  `onConflict: 'fcm_token'` upsert already makes re-registration idempotent.
- Prune on the send path instead: walk `sendEachForMulticast`'s per-token
  responses and delete the tokens FCM reports as
  `messaging/registration-token-not-registered` (and
  `messaging/invalid-argument`). This is the authoritative signal and it cannot
  delete a live device's token.

**Verify:** Both functions deploy; a send with a deliberately bogus token prunes
only that row.

**Done:** One user can hold an iPhone token and an Android token simultaneously.

## Must-haves

- A tappable Android path that results in a `device_tokens` row
- Token registration happens automatically once a session is known and
  permission is granted
- `enablePush` returns `'granted'` only when the row was written
- Registering on one device never deletes another device's token
- Invalid tokens pruned from FCM's own error codes
- `npm run build` and `npm run lint` green

## Out of scope

- Recording the real platform (`'android'` / `'ios'`) instead of `'web'` in
  `device_tokens`. Useful for debugging, but it is a data-semantics change and
  `notify-donors` does not filter on the column, so it is not needed to fix
  delivery. Noted as a follow-up.

## Manual retest (user)

After deploy, on the Android device: open the app logged in. If notification
permission is already granted, a token should appear with no interaction. Then:

```sql
select profile_id, platform, created_at, left(fcm_token, 12) as prefix
from device_tokens order by created_at desc;
```

Expect **two** rows for the same `profile_id` — one per device — and both to
survive the other registering. Then post a matching request and confirm both
phones alert.
